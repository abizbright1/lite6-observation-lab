Lite 6 visual experiment laboratory

This is the 3D visual simulation requested for the robot-observation research project: an articulated Lite 6, wrist camera, tabletop environment, stationary target and reference view. It supplements the earlier numerical lessons. The camera panels are rendered from the virtual scene; they are not live hardware streams.

The robot meshes and nominal kinematics come from the shared GitHub sample, with official UFACTORY asset provenance checked. Read ASSET_SOURCES.md for the user's fork versus shared upstream distinction, pinned source commits, byte comparisons and licenses.

Open the hosted scene

Use the 3D Studio link above. The site loads its static model and JavaScript from GitHub Pages, so no laptop web server is needed. Your browser still performs the simulation and WebGL rendering on its device. This is not cloud GPU computation. Pause the scene or close the tab when finished.

For local development, run python3 simulation/scene3d/serve.py from a repository checkout. The hosted site needs no robot SDK, ROS, connected camera or account sign-in.

Hosted viewing and local resource use

A verified GitHub Pages deployment can serve this viewer without running the local Python server. GitHub documents Pages as static hosting for HTML, CSS and JavaScript. The inspected scene still executes its kinematics and WebGL rendering in the viewing browser: hosting moves file delivery off the laptop, not the 3D computation onto a cloud GPU. A hosted viewer therefore still uses the viewing device's CPU/GPU and energy. This guide does not claim a live deployment until its URL is verified in the project record.

The resource-conscious default uses 1× pixel density and no rendered shadows. While paused, there is no recurring simulation timer or continuous render loop; the scene redraws for a view/control change. While playing, the world advances at a 30 Hz logical step and camera views/capture update at 10 Hz in simulation time. Hiding the tab pauses playback, and returning does not automatically resume it. Lower-resource mode can reduce rendering work, but no measured wattage, battery-life improvement or zero-energy claim is made. Downloads remain local synthetic exports; the viewer does not automatically upload them to GitHub.

The panels are numbered: environment, current wrist exposure, received evidence, experiment controls and independent reference view. Distances are millimetres, joint readouts are degrees and event timestamps are simulation seconds. A paused simulation time is not wall-clock latency or a measured hardware delay.

The point alignment test uses ±3 mm on each X/Y axis, a square success region. The displayed evaluator distance may be radial; that is a separate descriptive number. Do not interpret it as the axis-wise test's threshold. This scene uses a simple point estimator, not the earlier numerical lesson's bounded-interval rule or the proposed full-joint research method.

Read the views correctly

The overview is the place to orbit, zoom and inspect the arrangement. The wrist view shows the current virtual camera's perspective. The received view uses actual saved canvas snapshots captured from that rendered wrist view at 10 Hz. Delivery delay selects an older snapshot; the frozen case retains its first delivered snapshot and original exposure time. The reference view is a separate virtual viewpoint used to understand the scene; it is not evidence that a real reference measurement has been validated.

The key distinction is between when an image was exposed, when it was delivered, and the camera/robot pose used to interpret it. During motion, using a delayed image with the current pose can shift the inferred target position. When the camera is stationary and the scene has not changed, age alone does not create that displacement. A geometric calibration bias can remain in either case.

The scene's projected feature is obtained from known virtual geometry. It is an oracle feature for a geometric lesson, not the result of a learned detector or a validated pixel-processing algorithm. The feature-noise control changes the reported pixel coordinate; it does not add noise to the rendered image. The wrong-association preset selects the distractor's projected feature, while the occlusion case tests obstruction of the feature ray by the designated virtual occluder. These lessons do not establish a detector's robustness to real images.

Work through the first visual experiment

  1. Start with the clean case. Locate the robot base, tool, wrist camera, stationary target, distractor, calibration/reference artifact and independent camera in the overview. Check where the target appears in the wrist view.
  2. Play the simulated camera motion. Compare the overview with the wrist view. Pause and name the base, tool, camera and target-plane coordinate frames.
  3. Add delivery delay. Compare the current and received images, then the reported exposure and decision times. Predict the direction of the target-estimation error before inspecting it.
  4. Try the frozen-frame case. The robot can change pose while the received evidence remains old. A fresh host event is not a new exposure.
  5. Add calibration bias separately from timing delay. Explain why stopping the camera does not remove a camera-to-tool mapping error.
  6. Try wrong association or occlusion. Explain why an unavailable or incorrect feature is a different problem from a small bounded localization error.
  7. Export a short synthetic record and identify which fields belong to the online observation, decision and evaluator-only truth. Keep that record as a learning result, not a measured robot trial. If using the received-frame image export, remember that it is an annotated synthetic teaching image, not a raw real-camera frame.

Use one fault at a time before combining them. Record a prediction, a visible result and one limitation in the existing study journal. Use the user-confirmed 3–4 hours each weekday, Monday–Friday, or 15–20 hours/week. Saturday and Sunday are off. The revised plan reserves 180 core minutes per weekday plus up to 60 optional minutes that same day; this visual practice is part of that allocation, not extra homework. The previous total-weekly interpretation is superseded.

Synthetic data and the truth boundary

The online geometric inverse uses a permitted pixel feature, a nominal camera pose and a known plane. True virtual target state is reserved for evaluation. Exported observations, decisions and evaluator quantities must retain those roles. A method must not read the hidden actual target or injected calibration error to make its decision.

The JSON contains public records with observation/decision blocks and a separate evaluator_only array. Its experiment configuration/fault-control settings are run provenance; they are not features to feed into a later model. The CSV contains event times, feature availability/pixels, estimated position, tool position and the point decision, with no hidden target/capture pose or false-approval label. Keep source episodes and their faulted copies in one split when building a later dataset.

Changing target, delay, bias or noise starts a new recording in this viewer. The rolling display history retains only a short image queue and a bounded record buffer. Export each named trial before changing conditions. JSON/CSV export is not a saved full image dataset; a single received-frame PNG includes the teaching overlay. A later reproducible image benchmark needs raw image files, frame IDs, camera/clock metadata, run manifests and an independent evaluation protocol.

The visual scene and the earlier planar_lab.py batch simulator are separate teaching tools with different documented models. Do not join their outputs as if they were one calibrated physical experiment. A 3D-rendered image is synthetic data; it does not establish an actual camera's timestamp accuracy, optics, sensor noise, reference uncertainty or real pick outcomes.

What this viewer establishes—and what remains open

It provides spatial understanding of the proposed apparatus, camera projection, observation history and selected error mechanisms. The nominal kinematic chain gives link poses, and numerical inverse kinematics can illustrate a candidate motion within its numerical limits. It is not a dynamics/contact simulator or a collision-clearance proof. A visible vacuum cup does not establish suction, seal or a completed pick. Numerical poses and speeds are lesson settings, not commands for the real arm.

The current physical setup, trustworthy exposure-to-action timestamps and independent reference remain unverified. Full joint timing/calibration inference and strong research baselines also remain separate work. The adviser should review each new implementation/result rather than carrying the earlier numerical simulator's acceptance into the 3D extension automatically.

Before real recording, use the physical setup and data protocol, the blank data templates and the latest adviser review. Keep stages distinct: visual simulation, saved-data replay, passive recording, shadow decisions and separately approved supervised physical trials.
