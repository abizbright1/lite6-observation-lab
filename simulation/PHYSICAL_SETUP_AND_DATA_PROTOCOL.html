3D StudioWeekday study plan

From the simulator to a measured robot experiment

Prepared 3 November 2026. This is an experimental design and learning protocol. The simulator is a simplified observation-and-decision model, not a validated digital twin, robot controller or hardware safety system. No equipment was operated or purchased in preparing it. A physical pilot needs the lab's operating approval, installed-system procedures and a supervising operator.

1. The first physical question

Keep the target static and the camera rigidly attached to the tool. At a fixed observation height and orientation, ask whether the lateral placement error can be judged from camera observations whose capture times and geometric mapping are uncertain. Begin with X/Y alignment in free space above the target. Leave contact, grasping, moving targets, yaw motion, changing height and full dynamics outside the first physical question.

The core situation is a static object viewed by a moving wrist camera. A stale observation corresponds to an earlier camera pose. This differs from a moving object viewed by a fixed camera; do not transfer equations between these cases without checking signs and frames. For an illustrative constant-velocity component, timing uncertainty contributes roughly speed × time uncertainty to lateral position uncertainty. Calibration error can remain even after the camera stops. Repeated target images cannot necessarily distinguish target location from camera-to-tool bias.

The first useful result may be that a genuinely fresh stationary observation already solves the practical problem. Retain that null result and the stop-and-fresh-observation baseline. Artificially enormous delays cannot establish that the station has an important unresolved timing problem.

A simple ruler or caliper can check static artifact spacing; it cannot provide time-resolved moving-tool ground truth. A second camera may be useful but is not automatically accurate or independent: quantify its geometry, lens distortion, clock, resolution and reference registration. Use the exact installed equipment manuals for power and connectors. This protocol deliberately supplies no wiring pinouts or electrical alterations. The manufacturer requires secure mounting and a workspace assessment; tool/camera clearances extend beyond the bare-arm envelope. See Lite6 installation and Lite6 safety.

Do not buy a GPU, PLC, motion-capture system, force sensor, new robot or new camera to start learning. First establish the task tolerance, existing inventory and the reference uncertainty needed to distinguish competing outcomes.

  Camera power/data uses its verified original connection.
  Reference data and fault-injection metadata go to evaluation storage.
  The decision method receives only the permitted observation stream.

Choose B for robot base, T for tool, C for wrist camera, W for the measured plane and R for the independent reference. Record a transform as T_B_C, meaning it maps a point expressed in C into B. For eye-in-hand geometry, T_B_C(t) = T_B_T(t) × T_T_C. Write units beside every translation and state angle units and axis conventions. Record the fixed plane height, tool offset and observation-height domain.

Camera intrinsics turn image coordinates into rays; extrinsic/plane geometry supplies metric locations. A pixel is not a millimetre. Store image resolution/crop and calibration hash together. Changing crop, scale, focus, mount or working height can invalidate the adopted local mapping. Do not overwrite working robot calibration for a practice exercise. OpenCV documents the distinction between intrinsic and extrinsic quantities and the use of known pattern dimensions; its hand-eye API also requires specific transform directions. See calibration tutorial and calib3d reference.

4. Timing: preserve the original events

The current inspected camera producer at Projects/lite6-lab-control/scripts/camera_preview.py assigns last_received = time.monotonic() after queue.tryGet(), then stores that value as frame time. It measures time since host dequeue, not time since exposure. A rapidly dequeued old image can therefore look fresh. This audit is read-only; no working application was changed.

For a separate research logger, preserve all available native metadata before image encoding. Luxonis documents getTimestamp() in the host-synchronized dai.Clock domain and getTimestampDevice() in the raw device monotonic domain. ImgFrame provides timestamp overloads with exposure offsets. Record which offset/convention is selected and test availability against the installed version. These API meanings do not establish a deterministic synchronization bound for this particular station. See DepthAI Device and ImgFrame.

exposure -> camera processing -> transport/buffering -> host dequeue
          -> detector completion -> decision -> command issue -> ACK
          -> physical settle/evaluation event (not implied by ACK)

Record domain identifiers, units, restart/session IDs and mapping uncertainty. Do not subtract raw device time from host time without a justified mapping. Do not assume Python time.monotonic() and dai.Clock.now() are interchangeable merely because both are monotonic. If robot telemetry has only a host receipt time, name it pose_receive_time; do not call it exact controller sample time. An SDK acknowledgement confirms a software event, not exact physical completion. Rolling-shutter/readout and exposure duration may also matter under motion; begin with slow motion and validate whether the local model is adequate.

5. Measurement and uncertainty budget

Before choosing a tolerance, state what is being measured: e.g. Euclidean tool-marker to target-centre distance in the fixed plane at a specified settled endpoint. For axis-wise tolerances use a rectangle; for radial tolerance use a disk. Do not switch definitions between methods.

ComponentHow to estimate/justifyRecord

Illustration only: if a reference component is bounded by 0.25 mm, geometry remainder by 0.40 mm, execution by 0.30 mm, and unresolved event timing is 8 ms at 20 mm/s, the timing term is 0.16 mm. A deliberately conservative additive budget is 1.11 mm. These numbers are not measured station performance or recommended operating speeds. They explain why a 1 mm claim would be unsupported under those assumed bounds. Use the appropriate propagation for the actual model; avoid counting the same source twice.

Keep standard uncertainties/confidence intervals distinct from deterministic set bounds. Root-sum-square calculations need their own dependence/model justification; adding worst-case bounds answers a different question. Repeated data support empirical uncertainty assessment but an observed maximum is not a guaranteed universal bound. NIST distinguishes Type A and Type B evaluations; neither label by itself establishes a worst-case guarantee. See NIST TN1297 section 2.

When the independently measured error is e_ref with a justified radial error bound U_ref, evaluate definite success when e_ref + U_ref <= tolerance, definite failure when e_ref - U_ref > tolerance, and otherwise label the result indeterminate. Preserve indeterminate trials rather than counting them as successes or deleting them. Use geometry-consistent inclusion tests for axis-wise regions. The simulator's hidden exact state is unavailable in real experiments.

For combined faults, first run one-factor examples to understand cause, then a small declared factorial/mixed design. Report combinations, not an unexplained aggregate difficulty score. A small matched set at several realistic magnitudes is more useful initially than thousands of unrealistic synthetic episodes.

The injected fault ledger is evaluator-only. A method may see an ordinary timestamp or ID that would actually exist at deployment; it must not see fault_type, true added delay, true bias, true target location or hidden correctness labels. Metadata corruption scenarios should state which provenance is trustworthy. If an attacker/replay overwrites IDs as well as pixels, a source-ID check cannot be assumed to solve it.

Do not induce errors by loosening mounts, disabling stops, changing controller clocks, creating collisions, changing suction wiring, obstructing a live robot or unexpectedly moving a target under motion. Any later physical perturbation needs a separate approved protocol. Fault replay can teach decision behavior without putting corrupted observations on a live command path.

8. Collection and comparison design

Use separate sessions for development, bound/calibration assessment and final evaluation. Split entire physical runs/days/configurations, not adjacent frames from the same video. Freeze mappings, thresholds and bounds before opening the final test results. Preserve a stationary fresh-observation session and intentional held-out violations. Changing the mount creates a new configuration group, not more samples of an unchanged calibration.

Start with an illustrative pilot design of 3 independent recording sessions and 5–10 episodes per selected condition, subject to lab access. This is a feasibility sample, not a defensible final sample-size claim. Use observed paired variability and the intended scientific effect to plan later replication. Thousands of frames from one run are not thousands of independent trials.

Compare methods on identical source histories, candidates, action budgets and outcome definitions. An age-compensating method needs the same permitted trajectory information as its comparator. A reacquisition baseline must receive the same maximum wait/deadline and the same opportunities for new observations. Label a stopped-camera observation separately from an algorithm's computational runtime. An offline full-joint reference solver remains a necessary research comparator even if this teaching simulator does not yet implement it.

Report episode counts, approvals, abstentions/timeouts, definite false approvals, indeterminate reference outcomes, observed error distributions, same-machine compute time and separate physical cycle time when measured. Show denominators. Do not report “zero risk” because no failures occurred in a small pilot. Describe performance for in-bound cases separately from intentional violations; a bound-based method cannot inherit a guarantee in violated cases.

9. Progression and run checklists

Stage A — offline: run simulator, explain one fault by hand, reproduce output, inspect a false approval or abstention, and prove that evaluation truth is absent from policy inputs. Exit: learner can map the simplified variables to physical events and identify missing realism.

Stage B — passive recording: with normal lab access, use stored or separately authorized read-only data. No command interface is added. Inventory camera/clock metadata, inspect reference feasibility, and validate schemas on a short recording. Exit: known units/frames, original capture metadata or explicit missingness, reference assessment and complete manifests.

Stage C — supervised shadow evaluation: lab operator conducts an already approved experiment; research methods only log hypothetical decisions. Before each session check calibration identity, reference readiness, original record integrity and common clock mapping. Exit: reference can classify outcomes and shadow comparisons are reproducible. No physical success is assigned to an action that was never executed.

Stage D — separately approved physical pilot: only after adviser/lab approval and station procedures. Freeze a small protocol, operator roles, workspace, stop conditions, maximum action budget and reference method. Preserve the existing physical E-stop and controller boundaries. Do not automatically resume after fault, stale evidence, uncertain pose or lost reference. An AI adviser cannot authorize hardware access or certify the installation.

After every session: verify expected files/frame IDs, clock resets, missingness and reference validity; write a short deviations note; hash raw files; preserve originals; make a replayable copy; do not tune against held-out outcomes. If reference or timestamp evidence is inadequate, stop the scientific claim and resolve measurement rather than hiding the limitation.

10. Four-week simulation-to-measurement module at 3–4 hours each weekday

The user confirmed 3–4 hours every Monday–Friday, or 15–20 reserved hours/week, with Saturday and Sunday off. The earlier total-weekly allocation is superseded. This module is a conditional 60–80-hour allocation after the relevant foundations; it is not a promise to finish physical validation or a dissertation in four weeks. It can replace corresponding simulation/metrology work in the final four weeks of the main plan, or be scheduled later when ready. Select one route with the adviser; do not stack both sets of assignments into the same weekday.

Each weekday reserves 180 core minutes: 15 recall/prediction, 45 selected reading or derivation, 15 break, 60 implementation/measurement-design work, 15 break, and 30 analysis/log/review. Up to 60 additional minutes may extend the same task on that weekday. Breaks are inside the budget. There are no weekend or hidden catch-up assignments.
